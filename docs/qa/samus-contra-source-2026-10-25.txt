Confirmed defect1: upward Wave loses world page
----------------------------------------------
Both pinned SamusShot.formWavePattern implementations assign full nx around
fixed centerX. Current SamusWeapons::WaveUp assigns only SmShotX. A legal
upward Wave center766, age2/polarity1 should be world772 (page3,low4), but
becomes page2,low4 and disappears despite remaining visible. First actual
CPU wrong erase: bank10 PC$ABEE -> SmShotType[2],$6B19 =0.
Native original55: actual Up+B creates center254; age2 expects260 but becomes
4 while camera133. Native erase callback resumes at$ABF1 (instruction$ABEE).

The same-PC helper computes signed new-low minus prior-low and adjusts the
page only on an actual wrap. The sinusoid's bounded per-update displacement
makes that signed delta unambiguous. It allocates no center-page RAM. SAMUS
bank10 was completely full; an8-byte prefix reuses unreachable15-byte head
probe padding, and a19-byte tail reuses unreachable20-byte resident post-BG
bridge padding in bank127. Every old entry/span remains fixed; no bank switch.

Confirmed defect2: Wave reads another projectile slot for terrain policy
-----------------------------------------------------------------------
BridgeShot intentionally returns X=0 for the shared Mega Man collision slot.
Its caller then reads SmShotType,X to decide whether Wave ignores ground.
A real Wave in Samus slot1/2 reads unrelated slot0, enters block collision,
gets impact3 on an original question block and is erased three updates later.
Both ActionScript constructors omit all ground hit-testables for Wave.

The five-byte gate now reads already-bridged MmBulletType==9. Its join/X ABI
and every following PC remain unchanged; normal/Long retain terrain impacts.
Page-only proposal00d22cc36369cc515bb1699639272629506c95ad268830020c4041ae97a98975
is REJECTED and retained to isolate this second bug. First actual CPU wrong
impact: bank10 PC$AA32 -> SmShotImpact[2],$6B34 =3. Actual native callback
resumes$AA35. Candidate normal/Long controls still collide and expire.
